# Orderit

A minimal inference engine for one model family on one GPU: the **Qwen3 dense** decoders, on an AMD Strix Halo (`gfx1151`, Radeon 8060S). Two checkpoints are served, `Qwen3-Embedding-4B` and `Qwen3-Reranker-0.6B`; the 4B reranker is the same family and also loads. Nothing here is general purpose and nothing runs anywhere else.

It replaces the two CPU-bound llama.cpp containers this machine currently uses. Measured here, that costs about **5.0 s** per 2.2k-token document on the CPU (`scripts/verify.sh`, step 6); the first request after a model load is slower still because the page cache is cold.

## What it is not

There is no KV cache, no decode loop, no sampling, no scheduler with admission control, no prompt cache, no speculative decoding, no chat template engine, no tool calling, no structured output. Both models do one forward pass over a sequence and read one row out of it. Everything the two reference projects spend their size on is absent here because the workload never touches it.

```
src/
  config.hpp      the two models' geometry, as constants
  half.hpp        fp16 / bf16 conversion, hand written
  reference.hpp   double-precision oracle for every operation
  weights.{hpp,cpp}   GGUF v3 over mmap, mapped read-only to the GPU
  tokenizer.{hpp,cpp} Qwen2 byte-level BPE, pre-tokenizer hand coded
  model.{hpp,cpp}     the 36-layer Qwen3 stack, CPU reference forward
  embed.{hpp,cpp}     the two heads: pooling, normalise, yes/no scoring
  kernels.hip         every GPU kernel, one file (not yet written)
```

## Building and running

Everything happens inside one container, derived from the ROCm toolbox that is already on this machine:

```sh
scripts/build.sh                                  # cmake + ninja in the dev image
scripts/hip-shell.sh                              # a shell in that image, with the GPU
scripts/hip-shell.sh 'build/release/orderit-bench all'    # the F0 roofline
scripts/hip-shell.sh 'ctest --test-dir build/release --output-on-failure'
```

`deploy/Dockerfile.dev` adds only what the ROCm toolbox lacks: the HIP development headers and `gfx1151` device bitcode, a host C/C++ toolchain, and a build system. ROCm itself is the toolbox's own 10.0 install.

**The GPU kernels do not exist yet.** Everything so far establishes that the data path is right and records what the hardware can do; from F4 on it is GPU work. The CPU forward is a test oracle and never ships.

## The rules this project holds itself to

**The reference is llama.cpp, not itself.** Every numerical gate is a cosine against vectors llama.cpp produced from the same GGUF. Agreeing with our own CPU path would only prove the GPU path matches the CPU path; agreeing with llama.cpp is evidence about the model. Fixtures are regenerated by `tools/make_*_fixture.py` against a running llama-server.

**A tolerance is never widened to admit a change.** If a kernel gets faster and its cosine drops, the kernel is wrong. gufo's rule, and the reason it exists: an optimisation that moves the answer is not an optimisation.

**Two implementations agreeing proves nothing.** The oracles in `reference.hpp` are written from closed forms that can be checked by hand, not from another copy of the same code.

**A missing checkpoint is a skip, never a pass.** Tests return 77 and CTest reports them as skipped.

## Two things already known that shape the rest

**int8 buys no throughput here, only memory.** Measured on this machine: 51.1 TOPS int8 against 47.4 TFLOPS bf16, a 1.08x ratio. So the weights are int8 Q8_0 for the RAM and not for the speed, and the entire cost of that choice - in-kernel dequant, the tiled activation layout - is justified by halving 15 GiB to 7.5 GiB.

**The reference prompt ends with `eos_token_id`, not the end-of-turn marker.** llama.cpp appends 151643; the end-of-turn token at 151645 is a different id, one below it, and pooling the wrong one drops the cosine from 0.99986 to 0.70591. For a single-token input this matters even more: llama.cpp evaluates two tokens, because it appends the end token, so a one-token probe that does not append it is comparing different things.

Also worth knowing: llama.cpp's `/embedding` applies no instruction template, so the embeddings the current pipeline indexes with were produced without one. F7 measures what that costs.
